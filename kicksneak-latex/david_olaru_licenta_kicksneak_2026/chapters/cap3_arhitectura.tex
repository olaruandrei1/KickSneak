\chapter{Arhitectura sistemului}

\section{Vedere de ansamblu}

Aplicația KickSneak adoptă o arhitectură distribuită hibridă. Aceasta combină stabilitatea și consistența tranzacțională a unui nucleu .NET 10 cu performanțele specifice ale unor microservicii în Go și Python, deservind două interfețe frontend independente realizate în React și Next.js. Sistemul este structurat pe patru niveluri funcționale principale:
\begin{enumerate}
    \item \textbf{Layer-ul de Prezentare (Presentation Layer)}: Storefront-ul client (React 18, TypeScript, Vite) pentru utilizatori și Admin Panel-ul (Next.js, TypeScript, Prisma) pentru moderare și management de stoc.
    \item \textbf{Layer-ul API (Core Backend)}: Scris în .NET 10, validează securitatea prin Firebase SDK și acționează ca un API gateway intern pentru microservicii.
    \item \textbf{Layer-ul de Servicii (Service Layer)}: Microserviciul de chat în Go (WebSockets) și microserviciul AI în Python (Flask/PyTorch) pentru recomandări.
    \item \textbf{Layer-ul de Date și Infrastructură (Data Layer)}: Centralizează persistența în PostgreSQL 16, cache-ul licitațiilor în Redis 7, căutarea în Elasticsearch 8 și stocarea de imagini în Azure Storage.
\end{enumerate}

\section{Stack tehnologic}

Fiecare componentă a sistemului KickSneak a fost selectată pe baza unui proces de evaluare tehnică riguros, asigurând un echilibru optim între performanță, compatibilitate și fiabilitate.

\begin{itemize}
    \item \textbf{React 18, Vite și TypeScript} (Storefront UI): React oferă un model declarativ stabil bazat pe componente pentru interfață. Vite garantează timpi de încărcare ultra-rapizi la dezvoltare prin utilizarea modulelor ES native, iar TypeScript asigură siguranța tipurilor la compilare, prevenind erorile runtime.
    \item \textbf{Next.js 14 și Prisma} (Admin Panel): Next.js utilizează randarea pe server (\textit{SSR}) pentru a spori securitatea în panoul administrativ, limitând expunerea codului sensibil pe client. Prisma servește ca ORM, generând automat tipuri statice direct din schema bazei de date.
    \item \textbf{.NET 10, EF Core și Dapper} (Backend Core): .NET 10 asigură un runtime de înaltă performanță pentru Minimal APIs. EF Core este ORM-ul principal pentru logica complexă, în timp ce micro-ORM-ul Dapper este folosit pentru performanță brută în execuția interogărilor SQL directe și a tranzacțiilor rapide.
    \item \textbf{PostgreSQL 16}: Bază de date relațională utilizată ca sursă principală de adevăr tranzacțional. Suportă structuri JSON pentru metadate dinamice și implementează securitatea la nivel de rând (Row Level Security) direct din motorul bazei de date.
    \item \textbf{Go} (Chat Service): Limbaj compilat cu performanțe remarcabile în procesarea concurențială. Este ideal pentru conexiuni WebSocket persistente datorită modelului CSP bazat pe goroutine-uri ușoare și canale de comunicare rapide.
    \item \textbf{Python, Flask și PyTorch} (AI Service): Python oferă ecosistemul optim pentru învățarea automată. PyTorch este utilizat pentru a rula modelul NCF de recomandări, iar micro-framework-ul Flask expune logica de inferență prin API-uri REST.
    \item \textbf{Elasticsearch 8}: Asigură motorul de căutare full-text secundar, indexând catalogul de produse pentru a permite căutări aproximative rapide bazate pe relevanță textuală.
    \item \textbf{Redis 7}: Bază de date in-memory utilizată pentru cache și pentru stocarea stării volatile a licitațiilor active, garantând tranzacții atomice cu latențe sub o milisecundă.
    \item \textbf{Ollama}: Rulează local modele mari de limbaj (cum ar fi \textit{llama3.1:8b}), garantând confidențialitatea totală a conversațiilor utilizatorilor și eliminând dependența de API-uri terțe.
    \item \textbf{Azurite}: Emulator local pentru Azure Storage. Expune API-urile pentru Azure Blob (stocare imagini produse) și Table Storage (jurnale de audit), asigurând compatibilitate completă cu deployment-urile cloud.
\end{itemize}

\section{Fluxuri de date end-to-end}

Pentru a înțelege cum interacționează componentele, sunt analizate în continuare cinci scenarii critice de rulare a aplicației.

\subsection{Scenariul 1: Căutare produs cu sugestii live}
\begin{enumerate}
    \item Utilizatorul introduce caractere în caseta de căutare din frontend.
    \item Pe client se aplică un mecanism de \textit{debouncing} de 300ms. Dacă utilizatorul continuă să scrie, nu se trimite niciun request.
    \item Când scrierea se oprește, clientul apelează prin SignalR metoda \texttt{SearchHub.SearchAsync(query)}.
    \item Backend-ul Core interoghează indexul Elasticsearch prin interogări de tip \texttt{multi\_match} cu parametrul \texttt{fuzziness} setat pe \texttt{AUTO} (pentru a tolera greșelile de tipar).
    \item Elasticsearch returnează documentele potrivite sortate după scorul BM25.
    \item Dacă utilizatorul are activat filtrul "Search with AI", backend-ul apelează suplimentar microserviciul Python la endpoint-ul \texttt{POST /api/recommend}, obținând o listă de ID-uri ordonate conform vectorului de preferințe al utilizatorului.
    \item Backend-ul re-mapează datele și le trimite înapoi prin conexiunea activă SignalR, rezultatele fiind afișate sub forma unui meniu dropdown instantaneu.
\end{enumerate}

\subsection{Scenariul 2: Cumpărare directă cu Stripe}
\begin{enumerate}
    \item Utilizatorul adaugă un produs în coș (stare sincronizată local și salvată în baza de date PostgreSQL prin backend).
    \item În pagina de checkout, utilizatorul introduce datele de livrare și alege plata prin card bancar, trimițând un request la backend-ul .NET pe endpoint-ul \texttt{POST /api/checkout/create-session}.
    \item Backend-ul validează stocurile și apelează API-ul Stripe pentru a genera o sesiune securizată de plată (\texttt{checkout.sessions.create}), trimițând metadata asociată comenzii (ID-ul comenzii interne și ID-ul utilizatorului).
    \item Stripe returnează URL-ul sesiunii de checkout. Backend-ul trimite acest URL clientului, care redirecționează utilizatorul pe pagina securizată Stripe.
    \item Utilizatorul introduce datele cardului pe pagina Stripe, beneficiind de autentificarea 3D Secure dacă este necesar.
    \item Stripe confirmă plata și redirecționează utilizatorul pe o pagină de succes din frontend.
    \item Asincron, serverele Stripe trimit un eveniment semnat criptografic de tip \texttt{checkout.session.completed} pe endpoint-ul de webhook al backend-ului \texttt{/webhooks/stripe}.
    \item Backend-ul validează semnătura webhook-ului, marchează comanda ca plătită (\texttt{Paid}) și trimite asincron un eveniment în \texttt{Channel<NotificationEvent>} pentru a notifica utilizatorul live prin SignalR și a genera factura în fundal.
\end{enumerate}

\subsection{Scenariul 3: Licitație cu auto-bid și auto-close}
\begin{enumerate}
    \item Vânzătorul creează o licitație. Backend-ul Core o persistă în PostgreSQL și, simultan, inițializează starea licitației în baza de date Redis sub cheia \texttt{auction:\{id\}} ca un hash ce conține oferta curentă, timpul de finalizare și ID-ul ultimului ofertant.
    \item Backend-ul înregistrează un job asincron în Quartz.NET programat să ruleze la data de expirare a licitației (\texttt{AuctionCloseJob}).
    \item Când un cumpărător vizualizează pagina detaliată, clientul React se conectează la SignalR Hub-ul \texttt{AuctionsHub} și se alătură grupului \texttt{auction-\{id\}}.
    \item Cumpărătorul plasează o ofertă. Request-ul ajunge la backend, care utilizează tranzacțiile Redis de tip optimistic locking (\texttt{WATCH / MULTI / EXEC}) pentru a asigura consistența concurențială:
    \begin{lstlisting}[language={[sharp]C}]
    // Cod conceptual de plasare bid in Redis
    db.Watch(auctionKey);
    var currentBid = db.HashGet(auctionKey, "currentBid");
    if (newBid > currentBid) {
        var transaction = db.CreateTransaction();
        transaction.HashSetAsync(auctionKey, "currentBid", newBid);
        transaction.HashSetAsync(auctionKey, "currentBidder", userId);
        bool success = transaction.Execute();
        // Daca success e false, tranzactia a esuat din cauza unui bid concurent
    }
    \end{lstlisting}
    \item Dacă pe licitație există setat un prag maxim de auto-bid de către un alt utilizator, sistemul verifică dacă noul bid este mai mic decât pragul respectiv și plasează automat o contra-ofertă în mod recursiv până când se stabilește un nou câștigător.
    \item Backend-ul notifică grupul SignalR \texttt{auction-\{id\}} cu noul status, actualizând ecranele tuturor utilizatorilor conectați în timp real.
    \item La data finalizării, Quartz.NET execută \texttt{AuctionCloseJob}, scrie starea finală din Redis în PostgreSQL, generează comanda automat pentru câștigător și închide licitația.
\end{enumerate}

\subsection{Scenariul 4: Chat user-admin (escalare)}
\begin{enumerate}
    \item Clientul React inițiază o conexiune WebSocket cu microserviciul Go la \texttt{/ws/user-chat}, trimițând token-ul JWT Firebase în query string.
    \item Serviciul în Go validează token-ul JWT și înregistrează sesiunea cu statusul activ în tabela \texttt{chat\_sessions} din PostgreSQL.
    \item Mesajele trimise de utilizator sunt persistate în baza de date și retransmise instant operatorilor conectați în Admin Panel Next.js prin WebSocket-ul dedicat (\texttt{/ws/admin-chat}), iar răspunsurile acestora urmează calea inversă.
\end{enumerate}
Detaliile tehnice complete ale microserviciului de chat sunt prezentate în Capitolul 8.

\subsection{Scenariul 5: Chat user-LLM (Ollama)}
\begin{enumerate}
    \item Utilizatorul deschide o conexiune WebSocket la Go Chat Service pe calea \texttt{/ws/ai-chat}.
    \item La primirea unui mesaj, Go Chat Service analizează intenția: dacă se solicită asistență umană, sesiunea este marcată cu \texttt{escalated=true} și redirecționată către operator.
    \item În caz contrar, se interoghează local API-ul Ollama (\textit{llama3.1:8b}), iar token-urile generate sunt trimise în timp real (\textit{streaming}) către client și apoi persistate.
\end{enumerate}

\section{Strategie de deployment și CI/CD}

Sistemul KickSneak utilizează Docker pentru un deployment local unificat. Un fișier \texttt{docker-compose.yml} configurează cele 12 servicii, iar scripturile de bootstrap (\texttt{setup.ps1} pentru Windows și \texttt{setup.sh} pentru Linux/macOS) automatizează instalarea dependențelor și asamblarea containerelor.

Configurările de mediu sunt stocate într-un fișier \texttt{.env}. Cheile private Firebase Admin SDK sunt codificate Base64 și decodificate direct în memoria RAM a backend-ului pentru a preveni salvarea lor în istoricul Git.

Arhitectura este compatibilă cu integrările CI/CD (GitHub Actions/Azure DevOps). Fiecare serviciu folosește un \texttt{Dockerfile} bazat pe build-uri multi-stage (Alpine runtime), facilitând testarea automată și publicarea imaginilor în registry.

\section{Persistență și Azure Storage}

\textbf{PostgreSQL 16} reprezintă sursa tranzacțională unică a platformei. Gestionează datele esențiale ale aplicației: utilizatorii și rolurile lor, catalogul principal de produse, comenzile, tranzacțiile financiare și sesiunile de chat.

\textbf{Redis 7} stochează în memorie datele volatile de înaltă frecvență. Gestionează licitațiile active pentru a suporta bid-uri concurente, păstrează token-urile JWT blocate (blacklisted) și servește drept cache pentru a reduce numărul de interogări pe PostgreSQL.

\textbf{Elasticsearch 8} stochează documentele JSON optimizate pentru interogări text. Indexează elementele de catalog (titlu, descriere, brand, taguri) pentru a oferi căutări full-text și sugestii live extrem de rapide.

\textbf{Azure Storage} (emulat prin Azurite) reține fișierele binare mari în Blob Storage (imagini de produse, fișiere din chat) și date nestructurate de volum mare în Table Storage (jurnalele de audit și istoricul securizat), degrevând baza relațională.
